# Severity находок слепого жюри сверять с деплой-конфигом

**Extracted:** 2026-07-24
**Context:** Свод результатов слепого параллельного жюри (`/review --jury`) — главный цикл ранжирует находки судей перед вердиктом.

## Problem
Слепой судья видит **только код** (по замыслу — против якорения), но НЕ видит деплой-конфиг. Из-за этого острота (severity) находки может быть завышена: код в вакууме выглядит хуже, чем в реальном пайплайне.

Кейс: судья compatibility пометил «`create_all` в прод-пути конфликтует с Alembic (пустой alembic_version → первая миграция упадёт `relation already exists`) → **high**». По коду — верно. Но `railway.json` содержит `preDeployCommand: alembic upgrade head` (и `Procfile` — `release: alembic upgrade head`): миграции гонятся **ДО** старта приложения, поэтому `create_all` в lifespan после них — безвредный no-op (checkfirst). Реальная острота — ниже заявленной high.

## Solution
При своде jury-находок, ДО эскалации в блокер, для находок про **схему БД / миграции / порядок старта / инициализацию** — сверять с деплой-конфигом, которого судья не видел:
- `railway.json` / `railway.*.json` — `preDeployCommand`, `startCommand`, `releaseCommand`
- `Procfile` — `release:`, `web:`, `worker:`
- `Dockerfile` — `CMD` / `ENTRYPOINT`, порядок шагов
- `Makefile` / CI-workflow — шаги деплоя/миграций

Находка остаётся валидной как улучшение (убрать двусмысленность), но её severity и формулировка «блокер» корректируются под реальный пайплайн. Это НЕ отмена находки — это калибровка остроты по контексту, который слепой судья принципиально не имел.

## When to Use
- Сводишь результаты `/review --jury` (или любого слепого/изолированного ревью).
- Судья вернул high про: `create_all`, `init_db`, `metadata.create_all`, старт схемы, миграции, порядок запуска процессов, дрейф схемы.
- Перед тем как написать «🛑 блокер» — проверь деплой-конфиг: возможно, пайплайн уже снимает остроту.

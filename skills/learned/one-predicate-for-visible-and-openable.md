# «Видно» и «открывается» — один предикат, а не два одинаковых условия

**Extracted:** 2026-08-08
**Context:** Разграничение доступа, где одна и та же сущность попадает в списки/выдачу поиска
и открывается точечным маршрутом. BoardMind, Фаза A (права на первичных сущностях).

## Проблема

Видимость сущности вычислялась двумя путями: индексом видимости для списков
(`VisibilityIndex.object_`) и ключами прав для точечных проверок (`_scope_keys`). Условия были
написаны так, чтобы «совпадать». Они разошлись **дважды за одну фичу**, каждый раз с новой стороны:

1. **Грант расширялся по цепочке, запрет — нет.** Я сознательно ввёл асимметрию (`for_grant=True`)
   ради удобства. Итог: отведённый по конфликту интересов открывал карточку объекта, потому что
   грант «протекал» через дочерние вопросы, а запрет — нет. Нашли все три судьи независимо.
2. **Обратная сторона, после фикса.** Карточку закрыли для ограниченных ролей
   (`sees_all + object_`), но выдача поиска осталась на старом `object_`. По гранту на вопрос
   пользователь получал заголовок и описание объекта — ссылкой в 404. Не «битая ссылка», а
   утечка полей сущности, которую ему не показывают.

Корень один: **два выражения одного правила**. Пока они существуют раздельно, каждая правка
одного — шанс развести их снова. Тесты это не ловят: обе ветки зелёные по отдельности.

## Решение

Правило превращается в **именованный метод**, и все потребители спрашивают его, а не
переписывают условие:

```python
class VisibilityIndex:
    def object_card(self, object_id) -> bool:
        """Открывается ли КАРТОЧКА — единственный источник истины."""
        return self.sees_all and self.object_(object_id)
```

Дальше `doc()` (поиск), список, связи, история версий зовут `object_card`. Расхождение
становится невозможным по конструкции: разъехаться нечему.

Где нужны РАЗНЫЕ ответы (например, в журнал доступа надо писать настоящую причину отказа:
«отвод» ≠ «роль сюда не ходит») — разделяй **шаги**, а не переписывай предикат:

```python
if not vis.object_(oid):        # отвод / нет видимости — настоящее правило в лог
    deny(..., resource=obj)
if not vis.object_card(oid):    # сам гейт — тот же метод, что у списка
    deny(..., rule="no_grant")
```

**Проверка на месте (30 секунд):** взять сущность, которую пользователь ВИДИТ в списке, и
открыть её точечным маршрутом. Ответы обязаны сойтись — в обе стороны. Оформляется тестом:

```python
assert (oid in listed) == (point_status == 200), "расхождение списка и карточки"
```

## When to Use

- Правишь фильтр видимости в списке / выдаче поиска — сразу проверь точечный маршрут, и наоборот.
- Появилось желание сделать проверку «чуть иначе для этого случая» (флаг `for_grant`,
  `include_children`, «здесь и так только админы») — это и есть момент расхождения.
- Ревью нашло «эндпоинт отдаёт то, что нельзя открыть» или «в списке нет, а по прямой ссылке есть».
- Сущность помечена как транзитная/выбрасываемая: соблазн «не полировать» максимален,
  а разъехавшиеся проверки в ней текут ровно так же, как в постоянной.

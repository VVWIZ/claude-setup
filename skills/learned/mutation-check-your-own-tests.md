# Проверять собственные тесты мутацией

**Extracted:** 2026-08-01
**Context:** Любой новый тест на инвариант, особенно после рефакторинга «одно значение → список» и на контроль доступа.

## Проблема
Тест был зелёным, выглядел осмысленным и НЕ проверял ничего. Два реальных случая за одну сессию:

1. **Дедуп по списку.** Тест «детект не предлагает уже связанный prior» использовал фейковый LLM-детектор, который всегда возвращал `index=1`, т.е. первого кандидата. А первый кандидат совпадал с первой связью. Старое поведение (`seen` только из ОДНОЙ связи вместо всех) тест бы прошёл — регрессия уехала бы в прод.

2. **Проверка доступа.** Тест «отвод блокирует действие с решением» сам проставлял `decision.object_id = oid` прямо в сторе. В проде это поле не заполняется никогда, поэтому проверка отвода была no-op — а тест был зелёный, потому что искусственно создавал состояние, в которое система не приходит.

## Решение
После написания теста **верни дефект** и убедись, что тест краснеет:

```
1. Внеси мутацию в проверяемое место (одна строка, пометь `# MUTANT`)
2. Прогони ТОЛЬКО этот тест — он обязан упасть
3. Верни код как было, прогони снова — зелёный
```

Если тест остался зелёным при мутации — он проверяет не то, что заявлено в его имени.

Мутации, которые ловят типовые фальшивки:
- список → взять только первый элемент (`{x[0]}` вместо `{всё}`);
- убрать проверку доступа / фильтр видимости;
- убрать `try/except`, `if not ...: raise`;
- поменять `and` на `or` в условии инварианта.

## Особый случай: половина фичи не участвует в расчёте
Тест «следующий цикл считается от даты И пробега записи» создавал напоминание
с периодом только в километрах. При нулевом периоде по месяцам дата в расчёт
не входит вовсе — удаление `if done.date != nil { at = *done.date }` оставляло
тест зелёным. Заголовок обещал две оси, проверялась одна, и непокрытой
оказалась основная (месячных категорий было 5 из 7).

Признак: тест заявляет несколько условий, а фикстура включает не все. Мутация
находит это за полминуты — слепое жюри нашло то же самое, но дольше.

## Особый случай: ожидание выведено из проверяемой константы
Мутация `30 → 31` не роняет тест, если обе даты в нём посчитаны от той же
константы: сдвигаются вместе, соотношение сохраняется. Границу такой тест
проверяет, значение — нет. Разбор и лечение —
[[test-expectation-derived-from-constant]].

## Особый случай: тест, который сам создаёт нереальное состояние
Если тест руками выставляет поле/флаг, который в проде выставляет система — он проверяет фантазию. Спроси: **приходит ли система в это состояние сама?** Если нет — перепиши тест так, чтобы состояние возникало штатным путём (через API/импорт/сервис), а не присваиванием в сторе. Родня [[di-wiring-never-called]] (там юнит-тесты сами инжектили зависимость и не ловили забытую проводку).

## Особый случай: мутировать НАДО на двух уровнях — реализацию И проводку
Правка «поведение в модуле + переключатель в вызывающем» требует ДВУХ мутаций:

```
1) сломать саму реализацию  → тест обязан упасть
2) убрать флаг/аргумент в вызывающем (маршрут, хендлер, DI) → тест обязан упасть
```

Тест только на сервис зелёный и при неподключённой правке: сервис умеет новое
поведение, а маршрут продолжает звать старый путь. Реальный случай: `search()`
получил `for_grounding=True`, юнит-тест сервиса это проверял, но если снять
аргумент на эндпоинте — сюит остаётся зелёным, а фича в проде не работает.
Поэтому в наборе обязан быть сквозной тест через эндпоинт/CLI, а не только
юнит. Родня [[di-wiring-never-called]] и [[build-pipeline-wiring-smoke-gap]].

## When to Use
- Написал тест на «учитываются все N», «дубли не создаются», «доступ запрещён».
- Добавил флаг/параметр в сервис и передал его из вызывающего (проверь ОБА).
- Ревьюер (или слепое жюри) говорит «тест проходит по неверной причине».
- Рефакторинг «одиночное поле → коллекция»: старое поведение обязано валить новые тесты.
- Перед тем как написать в отчёте «покрыто тестами».

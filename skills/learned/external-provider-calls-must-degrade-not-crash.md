# Внешний провайдер в запросе должен деградировать, а не валить 500

**Extracted:** 2026-07-27
**Context:** BoardMind (FastAPI). Семантический поиск (`/search`, `/search/answer`)
через эмбеддинги Voyage. LLM-путь был обёрнут (`_llm_guard`: anthropic-ошибки → 502/429),
а путь эмбеддингов — НЕТ. Баг всплыл под синтетическим трафиком: 13× HTTP 500.

## Problem
`voyageai.error.RateLimitError` (free-tier Voyage без карты = **3 запроса/минуту**)
поднимался из `EmbeddingRanker.rank` → `SearchService.search` → **необёрнутый** →
FastAPI отдавал **500 Internal Server Error**. Ключевая фича (поиск) полностью
ломалась, как только пользователь искал чаще 3 раз/мин — тривиально достижимо.

Корень — **несогласованность guard-ов**: один внешний провайдер (LLM) защищён,
другой (эмбеддинги) — нет. Классическая дыра «добавили новую интеграцию, забыли
про обработку её отказов», невидимая в юнит-тестах (там фейковый провайдер, который
не бросает) и в ручном смоуке (один-два запроса не превышают лимит).

## Solution
Обернуть вызовы провайдера в горячем пути и **деградировать**, а не падать. Для
поиска надёжнее фолбэк (поиск продолжает работать хуже), чем 429/503 (базовая функция
отваливается из-за лимита стороннего сервиса):

```python
class EmbeddingRanker:
    def __init__(self, provider, *, fallback: Ranker | None = None, ...):
        self._fallback = fallback or StemmedLexicalRanker()

    def rank(self, query, texts):
        if not texts:
            return []
        try:
            query_vec = self._provider.embed_query(query)
            ...  # embed_documents
        except Exception as exc:  # noqa: BLE001 — деградация вместо 500
            _logger.warning("фолбэк на лексику: %s: %s", type(exc).__name__, exc)
            return self._fallback.rank(query, texts)
        ...
```

Широкий `except Exception` здесь оправдан: цель — «запрос не должен падать из-за
провайдера». Логируем тип+сообщение (диагностируемость), деградируем предсказуемо.

## When to Use
- Любой вызов внешнего сервиса (эмбеддинги, LLM, платёжка, геокодер…) в обработчике
  запроса. Всегда спрашивать: «что вернёт эндпоинт, если провайдер бросит/затормозит?».
- **Аудит существующих интеграций:** если один внешний путь обёрнут (`_llm_guard`),
  прогрепать ВСЕ вызовы провайдеров и убедиться, что защищены единообразно — новые
  провайдеры легко добавляют без guard-а.
- Выбор деградации: **фолбэк** (функция работает хуже) предпочтительнее **429/503**
  (функция отваливается), если есть осмысленный запасной путь.
- **Как ловить:** прогон синтетического трафика по проду + чтение логов (`ERROR`/
  traceback) вскрывает необёрнутые пути, которые юнит-тесты с моками пропускают.
  Тест-регресс: фейковый провайдер, который БРОСАЕТ → эндпоинт возвращает результат,
  не исключение.

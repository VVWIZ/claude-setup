# React Native iOS DateTimePicker: «отскок» спиннера — причина оказалась в maximumDate

**Extracted:** 2026-07-19, **найдено после 4 промахов** (2026-07-21). Диагностика на устройстве (панель value/draft/picked/tz) показала: значение схлопывается к ТЕКУЩЕМУ времени. Причина всё это время была не там, где я искал.

## Problem (настоящая причина)
`<DateTimePicker mode="date" maximumDate={new Date()} value={...} />` на iOS. `new Date()` — это текущий момент **со временем** (напр. 06:00 утра). iOS считает `value > maximumDate` недопустимым и **схлопывает** значение к `maximumDate`. Симптомы, которые сбивали с толку:
- «колесо времени отскакивает к 06:00» — на самом деле к `maximumDate` (= текущее время, у пользователя было раннее утро);
- «поменял дату — всё сломалось» — смена даты уводила момент за `maximumDate` → клэмп к «сейчас».

### ⚠️ Ложный след (на что я убил 4 итерации)
Я думал, что дело в «контролируемом value» iOS-спиннера (следует/не следует за колесом, коммит на каждый tick vs по «Готово»). Городил внутренний `draft`, замораживал value, менял момент коммита — **ничего не помогало, потому что `maximumDate` не трогал**. Урок: когда колесо «отскакивает к КОНКРЕТНОМУ времени» (особенно похожему на текущее) — **первым делом смотреть `minimumDate`/`maximumDate`**, а не механику value.

### 🔁 Кусало ТРИЖДЫ + конфликт с compact — ФИНАЛЬНОЕ решение
Клубок из двух багов в одном месте (комбинированный редактор даты+времени):
- **compact-пикеру (`display="compact"`) НУЖЕН `maximumDate`**, иначе он не применяет `value` и показывает **1970**.
- НО `maximumDate={new Date()}` несёт ТЕКУЩЕЕ ВРЕМЯ; когда `value` тоже со временем и оно позже текущего часа → `value > maximumDate` → клэмп + ре-рендеры → соседнее **колесо времени** отскакивает к ~6:00.
- Убрать maximumDate → возвращается 1970. Добавить `new Date()` → ломается время. Туда-сюда.

**Решение (намертво): `maximumDate` нормализовать к КОНЦУ ДНЯ** — `new Date(y, m, d, 23,59,59,999)`. Тогда: пикер заякорен (дата видна, не 1970); `value` любого времени сегодня < конца дня (клэмпа нет, время не ломается); max стабилен в течение дня (нет дёрганья). Сделать это ВНУТРИ общего DateField, чтобы вызывающие спокойно передавали `maximumDate={new Date()}`. (1970 дополнительно страхует guard `year<2000→today`, но сам по себе он не заставит compact показать value — нужен именно maximumDate.)

### 🏁 ИТОГ: `display="compact"` (всегда смонтированный) — хрупок, ушли на on-demand модалку
Даже с нормализацией max, compact-пикер (контролируемый value + асинхронный React-стейт + всегда смонтирован) давал новые гонки: выбор даты откатывался к дефолту (pick 21 → назад 22), баги «плавали» после навигации/hot-reload. Плюс dev-туннель Expo обрывался и крутил СМЕШАННЫЙ старый/новый JS — это маскировалось под баги кода (важно: сначала чистый холодный перезапуск, потом выводы). **Финальный надёжный паттерн: НЕ держать пикер смонтированным. Поле — просто чип с датой; тап открывает пикер в ОТДЕЛЬНОМ окне (`<Modal>` + `display="inline"` календарь на iOS / нативный диалог на Android), пикер живёт только пока окно открыто.** Плюсы: нет постоянных контролируемых гонок; окно-оверлей не двигает layout; закрытие календаря тапом мимо не роняет форму (разные окна). Минус — вложенная модалка (календарь поверх формы); present-over-present на iOS обычно ок.

## Solution
Убрать `maximumDate` (будущую дату ловить валидацией при сохранении), ЛИБО задавать его концом дня, а не моментом:
```tsx
// ПЛОХО: несёт текущее ВРЕМЯ → клэмп значения к «сейчас»
<DateTimePicker mode="date" maximumDate={new Date()} value={draft} />
// ХОРОШО (если нужно запретить будущие ДНИ): конец сегодняшнего дня
const endToday = new Date(); endToday.setHours(23,59,59,999);
<DateTimePicker mode="date" maximumDate={endToday} value={draft} />
// ИЛИ проще: без maximumDate, а будущее ловить на save (future_time alert)
```
Дополнительно (здоровая гигиена контролируемого спиннера, но НЕ причина бага): value ведёт внутренний `draft`, из пропа сеется только при открытии — тогда перерендер родителя колесо не дёргает.

## When to Use
- Жалоба «время/дата на iPhone отскакивает/сбрасывается к текущему времени (06:00 и т.п.)» → проверить `maximumDate`/`minimumDate`: не заданы ли они как `new Date()` (с временем).
- Правило: для ограничения по ДНЯМ `maximumDate` должен быть концом дня (23:59:59), а не моментом; иначе времена «сегодня, но позже сейчас» схлопываются.
- Общий класс «iOS-нативный рантайм, tsc/jest зелёные» → верифицировать на устройстве; когда воспроизвести не могу — встроить временную панель (value/draft/picked/tz) и получить данные с устройства, а не гадать. Родня: [[feedback-verify-runtime-not-green-tests]].

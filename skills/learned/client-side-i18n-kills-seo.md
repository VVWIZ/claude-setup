# Клиентская мультиязычность = вторая версия невидима для поиска

**Extracted:** 2026-07-18
**Context:** Двуязычный (RU/EN) лендинг: один URL, словарь `{ru,en}` в JS, переключатель в шапке подменяет `textContent` по `data-i18n`.

## Problem

Схема «один URL + JS-переключатель» отлично работает для людей, но для SEO это **одна страница на одном языке**:

- В HTML физически лежит только **дефолтный** язык (у нас русский) — его и индексируют.
- Вторая версия существует лишь как строки в JS-словаре → **у неё нет своего URL**, её нельзя показать в выдаче, на неё нельзя сослаться.
- `hreflang` не спасает: он требует **разных URL** на язык, а их нет.

Итог: англоязычный трафик из поиска не придёт в принципе, хотя перевод сделан и «на сайте есть».

## Solution

Если нужен поисковый трафик на втором языке — **отдельные URL**:

```
/            → русская версия (статический RU-текст в HTML)
/en/         → английская версия (статический EN-текст в HTML)
```

+ взаимные `hreflang` в `<head>` обеих страниц:
```html
<link rel="alternate" hreflang="ru" href="https://site.com/">
<link rel="alternate" hreflang="en" href="https://site.com/en/">
<link rel="alternate" hreflang="x-default" href="https://site.com/">
```
+ обе страницы в `sitemap.xml`, у каждой свои `title`/`description`/`og:*`.

Переключатель языка тогда — обычная ссылка между URL, а автоопределение по `navigator.language` может делать **редирект** новичка на нужную версию (но не блокировать краулеру доступ к обеим).

## When to Use

- Делаю мультиязычный сайт → сразу решить: JS-переключатель (только UX) или отдельные URL (UX + SEO).
- Вопрос «почему англоязычная версия не в поиске».
- Клиентский рендеринг контента вообще: **что не лежит в статическом HTML — того для поиска почти нет**.

## Trade-off

JS-переключатель проще (один файл, нет дублей) и годится, если второй язык нужен **только** для рекламного трафика/удобства. Отдельные URL — дороже в поддержке, но единственный путь к органике на втором языке.

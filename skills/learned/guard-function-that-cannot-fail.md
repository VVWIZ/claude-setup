# Сторож, который не может покраснеть

**Extracted:** 2026-08-12
**Context:** Проверки полноты словарей i18n (три языка), сканеры исходников на существование ключей перевода. Применимо к любой «мета-проверке»: линтер на тесте, проверка консистентности схемы, сверка контрактов.

## Problem

Проверка вида «собери список проблем и потребуй, чтобы он был пуст» имеет два независимых способа стать вечнозелёной, и оба не видны глазом:

**1. Сторож читает глобальное состояние.** Функция `missingTranslations()` берёт словари из модуля. Проверить её саму нечем: подмени тело на `return []` — тест полноты зелёный навсегда, и весь контроль держится на непроверенном коде. Особенно опасно, когда на эту проверку ссылается продуктовое решение («словари полны, значит можно показывать выбор языка»).

**2. Список пустеет при поломке ПОИСКА, а не при отсутствии проблем.** Сканер исходников ищет ключи регуляркой и копит ненайденные в словаре. Смени кавычки в регулярке (правдоподобное последствие смены стиля в prettier), префикс ключей или перенеси файлы в подпакет — совпадений ноль, список пуст, тест зелёный и не проверяет ничего.

Обе ловушки переживают обычный мутационный прогон по продуктовому коду: ломаешь продукт — сторож честно краснеет; ломается сам сторож — тишина.

## Solution

**Сторож принимает проверяемые данные ПАРАМЕТРОМ**, а обёртка без аргумента остаётся для обычного вызова:

```go
func MissingTranslations() []string { return MissingIn(catalog) }  // обёртка
func MissingIn(c Catalog) []string { ... }                          // проверяемое
```

Тогда рядом пишется тест с ЗАВЕДОМО БИТЫМИ данными: каждая проверка обязана найти свою поломку и **не найти чужую** (последнее не менее важно — иначе одна проверка маскирует отсутствие другой).

**Сканер считает найденное и требует нижнюю границу**:

```ts
const LEAST_KEYS = 150;           // запас к фактическим 265
expect(found.size).toBeGreaterThan(LEAST_KEYS);  // сначала это
expect(unknown).toEqual([]);                     // и только потом это
```

Граница нарочно грубая: она ловит ОБНУЛЕНИЕ поиска, а не считает ключи. Точное число пришлось бы править при каждом добавлении, и его начали бы подгонять под факт.

Сторожить надо ту ось, которая может выродиться. Проверка «пространств имён больше 20» держалась на размере словаря и стояла независимо от того, нашёл сканер тысячу совпадений или ноль.

## Example

```ts
// Каталоги битые намеренно; каждая проверка бьёт по своей ветке.
const ok: Catalogs = {
  ru: { 'a.n': '{n} штука|{n} штуки|{n} штук' },
  kk: { 'a.n': '{n} дана|{n} дана' },
  en: { 'a.n': '{n} item|{n} items' },
};

it('нехватка формы найдена — и именно ею, а не проверкой подстановок', () => {
  const broken = { ...ok, ru: { 'a.n': '{n} штука|{n} штуки' } };
  expect(mismatchedFormCountsIn(broken).join(' ')).toContain('ru:a.n');
  expect(mismatchedPlaceholdersIn(broken)).toEqual([]);  // чужая молчит
});
```

## When to Use

- Пишу функцию, чей смысл — «вернуть список проблем» (полнота переводов, сверка схемы с кодом, поиск мёртвых ключей, консистентность контрактов).
- Пишу тест, который сканирует файлы/исходники и на что-то жалуется.
- Вижу в тесте `expect(x).toEqual([])` / `if len(problems) > 0 { t.Error(...) }`.
- Ссылаюсь на такую проверку, обосновывая продуктовое решение («тест гарантирует полноту, поэтому включаем фичу») — тогда сторож обязан быть проверен вдвойне.

**Мутации для самопроверки:** тело сторожа → `return []`; регулярка сканера → заведомо непопадающая; фильтр по типам файлов → пустой. Если после любой из них всё зелёное — сторожа нет.

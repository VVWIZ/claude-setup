# pgx v5: uuid из `rows.Values()` — это `[16]byte`, а не строка

**Extracted:** 2026-07-31
**Context:** Go + `jackc/pgx/v5` (проверено на v5.10.0). Обобщённая правка строки: прочитать старые значения колонок → выполнить UPDATE → записать в аудит «было → стало».

## Problem

Код читает старые значения через `rows.Values()` (когда набор колонок динамический и типизировать заранее нечем) и сравнивает их с новыми, пришедшими из JSON-тела запроса:

```go
if fmt.Sprint(oldVal) == fmt.Sprint(newVal) {
    continue // «ничего не изменилось» — события не пишем
}
```

Для `text`/`bool` работает. Для `uuid` — **не работает никогда**: pgx декодирует uuid-колонку в `[16]uint8`, и

```
fmt.Sprint(old) = "[229 229 229 229 229 229 229 229 229 229 229 229 229 229 229 229]"
fmt.Sprint(new) = "e5e5e5e5-e5e5-e5e5-e5e5-e5e5e5e5e5e5"
```

Последствия тихие и двойные: (1) гард «поле не изменилось» не срабатывает — на каждый PATCH пишется ложное событие изменения; (2) в JSON-метаданные уезжает массив из 16 чисел вместо читаемого идентификатора, то есть ровно то «было → стало», ради которого всё и затевалось, становится бесполезным.

Проверяется за минуту:

```go
m := pgtype.NewMap()
dt, _ := m.TypeForOID(pgtype.UUIDOID)
v, _ := dt.Codec.DecodeValue(m, pgtype.UUIDOID, pgtype.TextFormatCode, []byte("e5e5…"))
fmt.Printf("%T", v) // [16]uint8
```

## Solution

Нормализовать значение из драйвера перед сравнением и записью, и **сравнивать по типам и значениям, а не по строковому представлению**:

```go
func normalizeValue(v any) any {
    if b, ok := v.([16]byte); ok {
        return uuid.UUID(b).String()
    }
    return v
}

func changed(oldVal, newVal any) bool {
    if oldVal == nil || newVal == nil {
        return oldVal != newVal
    }
    if reflect.TypeOf(oldVal) != reflect.TypeOf(newVal) {
        return true
    }
    return oldVal != newVal
}
```

Тест пишется без БД: подать `[16]byte` и строку, проверить что «то же значение» → не изменение, «другое» → изменение.

## Why it matters

`fmt.Sprint` для сравнения разнотипных значений — тихий баг по построению: он **всегда** даёт ответ и никогда не даёт ошибку. Помимо uuid он же считает равными число `1` и строку `"1"` — то есть класс дефекта шире одного типа.

## Generalization

**Значение из драйвера БД и значение из HTTP-тела — разные представления одного факта; сравнивать их можно только после явной нормализации.** Кандидаты на ту же ловушку: `numeric` → `pgtype.Numeric`, `timestamptz` → `time.Time` против RFC3339-строки, `jsonb` → `[]byte`, массивы. Правило: если сравниваешь `any` из БД с `any` из запроса — сначала приведи оба к каноническому виду, и никогда не делай это через строковое форматирование.

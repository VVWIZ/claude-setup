# Одноразовый bearer-токен: claim-last + компенсация

**Проблема.** Одноразовая ссылка/токен (курьерский доступ, инвайт, one-shot действие) должна сработать ровно один раз, но:
- Наивный «сначала пометить used, потом сделать» → перебор чужого/невалидного ID **сжигает чужой** токен ещё до проверки прав.
- Наивный «сделать, потом пометить» → гонка: два параллельных запроса оба проходят проверку `used IS NULL` и оба выполняют действие.
- Если действие после пометки провалилось (устройство offline, внешний сбой) → токен сгорел зря, повтор невозможен.

**Решение — три правила:**

1. **Claim последним шагом.** Порядок в обработчике: найти токен → провалидировать окно/отзыв → **зарезолвить/проверить права на конкретную цель** → и ТОЛЬКО потом атомарный claim → выполнить действие. Так мусорные/чужие запросы отсекаются до сжигания.

2. **Claim — атомарный conditional UPDATE, не SELECT-then-UPDATE.** Один запрос делает и проверку, и запись; полагается на row-lock БД:
   ```sql
   UPDATE t SET used_at = $now
   WHERE id = $1 AND used_at IS NULL AND revoked_at IS NULL AND expires_at > $now
   RETURNING used_at
   ```
   0 строк → уже использован/отозван/истёк. Второй параллельный запрос блокируется на row-lock, после коммита первого перечитывает WHERE → 0 строк. Гонка закрыта самим Postgres, Redis/SET NX не нужен.

3. **Компенсация при неудаче действия.** Если действие после claim вернуло ошибку — откатить `used_at = NULL`, но **только когда точно известно, что действие не произошло**. Это требует ЯВНОГО контракта у вызываемого: «ошибка ⇒ побочный эффект не случился». Откат гвардить по значению и по не-отозванности:
   ```sql
   UPDATE t SET used_at = NULL WHERE id = $1 AND used_at = $claimed AND revoked_at IS NULL
   ```
   Guard `used_at = $claimed` (возвращённое из RETURNING значение, не исходный now() — микросекундная точность round-trip совпадёт) + `revoked_at IS NULL` (не воскрешать отозванный, если его отозвали между claim и откатом).

**Ключевой момент про контракт.** Компенсация безопасна, только если у действия задокументирован инвариант «error ⇒ эффекта не было». В QR-домофоне это `access.OpenResolved`: ошибка означает, что MQTT-команда физически не публиковалась. Инвариант закреплён doc-комментарием + тестом с mock, возвращающим ошибку «после диспатча» — иначе будущий рефакторинг (сделать best-effort-ошибки блокирующими) тихо сломает компенсацию и создаст риск двойного эффекта.

**Остаточный край (принять осознанно).** Если первый запрос сделал claim и получил ошибку (компенсирует), параллельный второй мог успеть увидеть `used != NULL` и получить спурьёзный «уже использовано». Крайне маловероятно (тот же клиент, ретрай), самоисправляется повтором. Не корректностный дефект.

**Проектный контекст:** `backend/internal/couriers/{service.go:OpenAsCourier, repo.go:ClaimOneTime/ReleaseOneTime}`, контракт — `backend/internal/access/service.go:OpenResolved`.

# Парные эндпоинты обязаны зеркалить проверки доступа

**Extracted:** 2026-08-01
**Context:** Добавление обратной операции к существующей мутации (link/unlink, grant/revoke, assign/unassign).

## Проблема
`POST /decisions/{id}/link-prior` проверял запрет (конфликт интересов) на **обоих** участниках — и на самом решении, и на прежнем. Добавленный позже `DELETE /decisions/{id}/link-prior/{prior_id}` проверял только первого: `prior_id` использовался просто как ключ поиска в списке.

Результат — односторонняя привилегия: отстранённый по конфликту интересов **не может поставить** связь, но **может её снять**. Причём необратимо (снятие связи не откатывает статус погашенного решения) и незаметно (конфликт исчезает из дашборда). Классическая асимметрия: при копировании обработчика проверки копируют не полностью.

## Решение
Написав обратную операцию, выпиши проверки прямой построчно и сверь:

| Прямая (POST) | Обратная (DELETE) |
|---|---|
| `_owned(decision)` | `_owned(decision)` |
| `role_can(...)` | `role_can(...)` |
| `_owned(prior)` | `_owned(prior)` ← **забывают** |
| `_enforce_not_denied(decision)` | `_enforce_not_denied(decision)` |
| `_enforce_not_denied(prior)` | `_enforce_not_denied(prior)` ← **забывают** |

**Порядок важен:** проверку доступа ставить ДО проверки существования связи/ресурса. Иначе код ответа становится оракулом — по 404 vs 403 отведённый узнаёт, существует ли связь с объектом, к которому его не пускают.

Тот же принцип шире: read-путь фильтруется по видимости, а write-путь — по деньаю; если добавляешь фильтр на одном, проверь второй (у нас `/conflicts` и `detect-links` фильтры получили, а `GET /suggestions` — нет).

## When to Use
- Добавляешь DELETE к существующему POST (или любую обратную операцию).
- Ревью диффа, где появился новый маршрут рядом с уже существующим.
- Слепое жюри вернуло находку «эндпоинт без проверки, в отличие от соседних».
- Проверка «может ли пользователь откатить то, что не может сделать?».

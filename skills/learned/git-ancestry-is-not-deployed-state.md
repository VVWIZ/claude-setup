# Предок в git ≠ применено на проде

**Extracted:** 2026-08-12
**Context:** Деплой Railway (миграции применяются при старте контейнера). Применимо к любому пайплайну, где миграции едут вместе с образом, а не отдельным шагом.

## Problem

Перед выкаткой возник вопрос: нужна ли колонка `users.lang`, есть ли она на проде. Рассуждение выглядело убедительным:

> Миграция `0015_language.sql` — предок текущего коммита (`git merge-base --is-ancestor` подтверждает), значит она уже на проде.

Это неверно, и ошибку сделали двое независимо: я и слепой судья ревью. `git merge-base` доказывает, что **код** содержит миграцию, и ничего не говорит о том, **какой образ сейчас запущен** и докатился ли его старт до применения миграций.

Фактически прод стоял на версии goose 14, колонок `lang` и `tg_lang` не было. То есть выкатка меняла схему — а я объявил её «без миграций».

Цена ошибки не в самой миграции (две nullable-колонки — безопасно), а в решении: «миграций нет» → «дамп не обязателен» → откатывать нечем.

## Solution

Состояние прода узнавать **у прода**, а не у истории:

1. Снять дамп (для Railway — `pg_dump` внутри контейнера БД через `railway ssh`: клиент и сервер по определению одной версии).
2. **Восстановить его в одноразовый контейнер и посчитать строки.** Непроверенный дамп бэкапом не является — и именно эта проверка вскрыла расхождение: запрос упал на `column "lang" does not exist`.
3. Посмотреть фактическую версию миграций и состав таблиц:

```sql
SELECT version_id, is_applied FROM goose_db_version ORDER BY version_id DESC LIMIT 3;
SELECT string_agg(column_name, ', ' ORDER BY ordinal_position)
FROM information_schema.columns WHERE table_name = 'users';
```

Побочная выгода: заодно узнаёшь настоящий масштаб данных. Я считал, что пользователей 16 (число из прошлой сессии) — оказалось 26.

## Example

```bash
sh scripts/dump-prod.sh                      # дамп из контейнера БД
docker run -d --name pg-check -e POSTGRES_USER=t -e POSTGRES_PASSWORD=t \
  -e POSTGRES_DB=restored postgres:18-alpine
docker cp dump.sql pg-check:/tmp/d.sql
docker exec pg-check psql -U t -d restored -v ON_ERROR_STOP=1 -q -f /tmp/d.sql
docker exec pg-check psql -U t -d restored -tAc \
  "SELECT count(*) FROM users"                # данные целы?
docker rm -f pg-check
```

На Windows/Git Bash пути внутрь контейнера искажаются — `MSYS_NO_PATHCONV=1` или PowerShell для `docker exec ... -f /tmp/...`.

## When to Use

- Перед любой выкаткой отвечаю на вопрос «есть ли здесь миграции» или «эта колонка/таблица уже на проде».
- Диапазон коммитов для ревью НЕ равен диапазону «что сейчас на проде → что выкатываем»: первый может не содержать миграций, второй — содержать.
- Опираюсь на число пользователей/записей из прошлой сессии — проверить, оно устаревает.
- Готов сказать «дамп не нужен, схема не меняется» — именно тогда и проверить.

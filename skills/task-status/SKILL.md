# Статус задачи

Отчёт человеку: что закрыто, что осталось, что мешает. Читается за минуту, каждый пункт — либо факт с доказательством, либо честное «нет».

## Границы

Это **отчётная** задача, не рабочая. Внутри скилла:

- **Ничего не править и не создавать.** Ни файлов, ни коммитов, ни деплоев. Нашёл недоделку — она идёт в чек-лист пунктом, а не в правку.
- **Не запускать субагентов и не лезть в сеть.** Отчёт собирается из того, что уже есть в сессии, плюс дешёвые локальные проверки. Единственное исключение — verify-агент (см. «Режим verify»), и только по явному согласию пользователя.
- **Не выводить файл.** Отчёт идёт в чат. Файл — только если пользователь прямо попросил, и тогда это отдельное действие после отчёта.

Смежные скиллы, которые здесь не нужны: `verification-before-completion` (гейт на одно заявление), `report` (аудит модуля в `_audit/`), `plan` (план на будущее, а не состояние сейчас).

## Источник истины — строго по приоритету

1. **Журнал действий этой сессии** — какие команды реально запускались и что вернули, какие файлы реально читались и правились. Это главный источник. Отчёт собирается по нему, а не по памяти о собственных намерениях.
2. **Файл плана / ТЗ / карточка Trello**, если задача из них выросла — оттуда берётся список того, что вообще должно быть сделано.
3. **Состояние системы** — дешёвые локальные проверки под конкретную задачу (см. ниже).
4. **Пересказ по памяти** — не источник. Если пункт не подтверждается 1–3, он не идёт в «Готово».

Если журнал сессии обрезан компакцией и часть работы в нём не видна — сказать это одной строкой в конце отчёта, а не додумывать. Формулировка: «Ранняя часть сессии сжата, статус по ней восстановлен по резюме — сверь сам».

## Шаг 1. Собрать факты

Пройди журнал сессии и выпиши, что фактически произошло: какие команды исполнились с каким результатом, какие файлы изменены, что вернули проверки.

Затем добери состояние **точечно, под задачу**. Не гони весь набор подряд — выбирай по типу работы:

| Тип работы | Чем добрать |
|---|---|
| Код в репозитории | `git status --short` и `git diff --stat` (что в рабочем дереве), `git log --oneline -10` (что закоммичено) — это два разных факта, не смешивать |
| Код перед сдачей | тест/линт/typecheck-команда **из проектного `CLAUDE.md` или манифеста** (`go.mod`, `package.json`, `pubspec.yaml`, `composer.json`) — не угадывать |
| Изменённые файлы | `grep -rn "TODO\|FIXME\|HACK\|WIP"` по ним — недоделки внутри «готового» |
| Сервер, деплой, инфраструктура | то, что уже спрашивали в сессии: статус сервиса, ответ эндпоинта, наличие файла на месте |
| Документ, ТЗ, план | файл существует и в нём есть нужные разделы — `Read` |

**Соразмерность доказательства.** Опечатка закрывается диффом. Фича — числами `pass/fail`. Миграция БД — версией и фактом применения. Деплой — ответом сервиса, а не «команда прошла без ошибок». Не требуй от мелочи тяжёлых пруфов и не закрывай крупное лёгкими.

Не гоняй заново то, что уже отработало в этой сессии, и не поднимай тяжёлое ради красоты отчёта. Если проверка дорогая и не запускалась — так и напиши, это метка `⚠️`, а не повод её запускать.

## Шаг 2. Разложить по меткам

Четыре метки, и границы между ними жёсткие:

| Метка | Когда | Обязательное условие |
|---|---|---|
| `✅` | Результат достигнут и подтверждён | Есть доказательство из шага 1 |
| `⚠️` | Работа сделана, но **конкретная проверка не гонялась** | Названо, какая именно проверки не хватает |
| `☐` | Не сделано | Названо, что для этого нужно |
| `⛔` | Заблокировано | Названа причина и что разблокирует |

`⚠️` — не «я не уверен». Это точный факт: правка на месте, а проверка не выполнялась. «Экспорт написан, `go test` не запускался» — это `⚠️`. Из-за отсутствия этой метки непроверенное падает либо в `✅` (вранье), либо в `☐` (тоже вранье).

**Формулировка пункта — результат, не активность.** Не «поправил `auth.go`», а «пользователь с истёкшим токеном получает 401». Не «настроил nginx», а «`api.example.com` отдаёт 200 по HTTPS». Активность скрывает, достигнут ли результат: файл поправить можно и не решив проблему.

Простыми словами, без жаргона там, где он не нужен. Технические идентификаторы — хосты, пути, имена файлов, версии — оставлять как есть в `коде`: они и есть конкретика.

## Шаг 3. Собрать «Дальше, по порядку»

Всё несделанное — это не список, а последовательность. Собери его так:

- Сгруппируй по домену или этапу: «DevOps — волна 2», «Бэкенд — гейт», «Чистка».
- Отсортируй **по зависимостям**: первым идёт то, что разблокирует остальное. Не по важности и не по размеру.
- Каждой группе — заголовок и одна строка контекста: сколько занимает, будет ли простой, зачем она вообще. `Простоя нет` · `Гейт для волны 3` · `Окно 10–15 минут`.
- Внутри группы — атомарные пункты `☐`, каждый в одну строку, с конкретными именами и путями.

Отдельно вынеси то, что **всплыло по ходу и не было в плане**. Чек-лист по мере работы растёт, а не сокращается — если всплывшее тихо дописать в старый список, потеря скоупа станет невидимой.

## Формат вывода

Первой строкой — вывод, потом всё остальное. Пустые секции удаляются целиком, заголовков-пустышек не бывает.

**Если спросили «всё сделано?»** — ответ это строка `СТАТУС:` и чек-лист под ней, а не «да». Голое «да» на такой вопрос — то самое ложное завершение, против которого весь скилл: вопрос закрытый, отвечать на него дешевле всего неправдой. `⚠️` и `☐` в списке и есть содержательное «нет, не всё», и они должны быть видны, а не растворены в тексте.

```
СТАТУС: <готово N из M> · <главный блокер или «блокеров нет»>

## Готово
- ✅ <результат> — <доказательство, коротко>
- ⚠️ <результат> — не проверено: <какой проверки не хватает>

## Дальше, по порядку

### 1. <Домен> — <этап>. <одна строка: простой / срок / зачем>
- ☐ <атомарный шаг с именами и путями>
- ☐ <атомарный шаг>

### 2. <Домен> — <этап>. <одна строка>
- ☐ <шаг>

## Заблокировано
- ⛔ <что стоит> — <чем именно>, разблокирует <кто/что>

## Всплыло по ходу — не было в плане
- <находка и что с ней делать>

## Нужно решение от тебя
- <вопрос> → мой дефолт: <вариант, который применю, если промолчишь>
```

Каждый вопрос в последней секции идёт **с дефолтом**, чтобы можно было ответить «по дефолту» и не думать. Вопрос без дефолта — это переброс работы обратно на человека.

**Если отчёт собирается из-за того, что человек уходит** («продолжу завтра», «на сегодня всё»), главной секцией становится «Дальше, по порядку»: первый шаг первой группы должен читаться как команда, с которой можно начать, ничего не вспоминая — с именами файлов, хостов и веток. Секцию «Нужно решение от тебя» в этом случае ставить **выше** «Дальше»: ответ на неё определяет, с чего начинать.

## Против воды

Числа, а не призывы к краткости:

- `## Готово` — максимум **12 строк**. Больше — сворачивай однотипное в одну строку («4 A-записи на 195: `omi-nish`, `hr`, `aho`, `amo`»).
- `## Дальше` — максимум **5 групп** по **6 пунктов**.
- Один пункт — **одна строка**. Не влезает — значит это два пункта или пункт с подпунктами.
- Свернул или урезал — **скажи, сколько и что** одной строкой. Молчаливое усечение читается как «это всё».

Запрещено в тексте отчёта:

- Пересказ процесса. Не «сначала я посмотрел логи, потом понял, что» — только результат.
- Оценочные прилагательные: `успешно`, `корректно`, `качественно`, `аккуратно`, `надёжно`.
- Хеджирование: `должен работать`, `вероятно`, `похоже`, `скорее всего`, `по идее`, `should pass`, `seems to`, `probably`.
- Вступления и итоговые абзацы. Отчёт начинается строкой `СТАТУС:` и заканчивается последним пунктом.

Слова `успешно` и `has been` — статистические маркеры ложного заявления о завершении. Если тянет их написать, значит на этом месте должно стоять доказательство или метка `⚠️`.

## Против ложного «готово»

Прежде чем поставить `✅`, проверь пункт на пять типовых провалов:

1. **Правка вслепую** — файл менялся без чтения. Изменение могло уйти не туда.
2. **Отчёт расходится с журналом** — в тексте «проверил», а в журнале сессии соответствующего вызова нет. Журнал сильнее текста. Это же касается отчётов субагентов: сверять с тем, что они реально вызывали.
3. **Проверка не запускалась** — «тесты написаны и проходят» без фактического прогона. Это `⚠️`, не `✅`.
4. **Собралось ≠ работает** — успешная сборка, линт и typecheck не значат, что сценарий проходит. Для UI и эндпоинтов нужен реальный проход, не компиляция.
5. **Только счастливый путь** — основной сценарий работает, пограничные случаи остались как `// TODO`. Это `⚠️` с названными пропусками, не `✅`.

Сомневаешься между `✅` и `⚠️` — ставь `⚠️`. Недооценить готовность дешевле, чем переоценить.

## Режим verify — независимая перепроверка

Когда запускается: пользователь вызвал `/task-status verify`, или согласился на предложение после обычного отчёта.

**После каждого обычного отчёта, где есть хотя бы один `✅`, — предложи одной строкой:**
«Прогнать verify — независимую перепроверку каждого ✅ по диску и git? (~1–2 мин)» — и жди ответа. Отказ — нормальный исход, не уговаривать. Не предлагать, если verify уже отработал в этом отчёте.

Как работает:

1. Запусти **один** Agent с `model: opus` — верификатор.
2. Передай ему **только формулировки `✅`-пунктов** и пути к репозиторию/файлам. **Свои доказательства и текст отчёта не передавать** — читая их, проверяющий соглашается с ними вместо проверки.
3. Задача верификатора — адверсариальная: «Попробуй ОПРОВЕРГНУТЬ каждый пункт по реальному состоянию: файлы, git, прогон проверочных команд. Ничего не правь и не удаляй. По каждому пункту верни: CONFIRMED + факт / REFUTED + факт / UNVERIFIABLE + причина».
4. Слей результат в отчёт: REFUTED → пункт переезжает из `✅` в `⚠️` или `☐` с фактом верификатора; UNVERIFIABLE → `⚠️` с пометкой «verify не смог проверить: <причина>». CONFIRMED ничего не меняет.
5. Покажи короткий блок: `Verify: подтверждено X из Y` + только изменившиеся пункты. Подтверждённое заново не перечислять.

Честное ограничение: верификатор не видит журнал этой сессии. Пункты, чьё доказательство существует только в журнале («команда вернула X», разовый вызов API), он честно вернёт как UNVERIFIABLE — это не ошибка, а сигнал, что след на диске или в git отсутствует.

## Самопроверка перед отправкой

- [ ] Каждый `✅` опирается на факт из журнала или на проверку из шага 1 — ни один не стоит на памяти
- [ ] У каждого `⚠️` названа отсутствующая проверка, у каждого `☐` — что нужно, у каждого `⛔` — причина и кто разблокирует
- [ ] Пункты сформулированы как результаты, а не как активности
- [ ] Первая строка — `СТАТУС:`, вступления нет
- [ ] Ни одного запрещённого слова
- [ ] Лимиты соблюдены; всё свёрнутое названо
- [ ] «Дальше» отсортировано по зависимостям, у каждой группы есть строка контекста
- [ ] У каждого вопроса есть дефолт
- [ ] Ничего не правил и не создавал

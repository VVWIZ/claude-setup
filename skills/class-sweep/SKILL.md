Задача: $ARGUMENTS

Правило, ради которого этот скилл существует: **чинится класс, а не экземпляр**. Пользователь сообщает об одной точке, но точка почти никогда не единственная. Пока остальные живы, они всплывают по одной и стоят пользователю новых кругов ручного тестирования — самого дорогого ресурса.

---

## Шаг 1. Назвать класс, а не симптом

Симптом — то, что увидел пользователь. Класс — то, что породило симптом.

| Симптом (так НЕ формулировать) | Класс (так формулировать) |
|---|---|
| «в приёме врача создаётся две записи» | формы с ленивым созданием записи не блокируют сохранение на время заливки |
| «клавиатура закрывается при вводе» | компонент объявлен внутри компонента → ремаунт на каждый рендер |
| «не принимает 37,8» | разбор пользовательского ввода через `Number()` без нормализации разделителя |
| «в прививках две иконки» | эмодзи зашит внутрь строки перевода |

Если класс сформулировать не удаётся — **это и есть главный результат шага**: значит причина ещё не понята, и чинить рано. Вернись к диагностике.

## Шаг 2. Найти ВСЕ вхождения

Поиском по коду, не по памяти. Подобрать 2–3 разных запроса: по имени функции, по конструкции, по соседнему признаку. Один запрос почти всегда неполон.

Искать и там, где симптом не проявлялся: класс мог не выстрелить из-за случайности (медленная сеть не совпала, оверлей случайно перекрыл кнопку) — такие места опаснее всего, потому что выглядят рабочими.

Проверить также:
- **зеркальные пути** — создание против правки, добавление против удаления;
- **однотипные экраны** — если правило введено на одном, оно должно быть на всех;
- **другой конец** — клиент и сервер, форма и API-обработчик.

## Шаг 3. Решить по каждому вхождению

Три исхода, третий обязателен к озвучиванию:

1. **Чиню** — та же болезнь.
2. **Не болеет по устройству** — объяснить, почему именно (не «вроде работает», а «здесь запись уже существует, создавать нечего»).
3. **Оставляю осознанно** — назвать причину и цену (риск, объём, зависимость от чужого решения).

## Шаг 4. Убрать возможность структурно

Если один и тот же класс требует одинаковой правки в N местах — это сигнал, что правку надо поднять уровнем выше: общий хелпер, общий компонент, проверка в одном месте. Тогда дефект не сможет вернуться в новом коде.

Не всегда оправдано: если мест два и они разные по смыслу, дешевле починить обе. Решение объяснить.

## Шаг 5. Отчитаться охватом, а не количеством

Показать таблицу: где искал, что нашёл, что сделал. Пользователь должен видеть **охват**, а не верить на слово.

```
| Место | Состояние | Действие |
|-------|-----------|----------|
| forms/A | болеет | починено |
| forms/B | болеет | починено |
| forms/C | не болеет — запись уже существует | не требуется |
| forms/D | болеет | оставлено: зависит от обновления библиотеки, см. HANDOFF |
```

## Шаг 6. Закрепить

- Если класс неочевиден и может вернуться — **комментарий в коде** рядом с защитой: что именно предотвращаем и как проявлялось.
- Если это грабля окружения/библиотеки — предложить `/learn`.
- Если правило про продукт (поведение экранов) — записать в документацию проекта.

## Правила

- **Не расширять задачу молча.** Аудит класса — не повод переписывать соседний код. Нашёл смежную проблему — назови её отдельно, не смешивай.
- **Не объявлять «готово» до шага 2.** Починенная точка без поиска остальных — незакрытая задача.
- **Тесты — на класс, где возможно.** Один тест на вынесенный хелпер надёжнее пяти проверок на каждое место.
- После правок — предложить `/review`, как обычно.

## Когда применять

- Любой баг-репорт от пользователя (по умолчанию, а не по особому случаю).
- Введение нового правила поведения: ограничение ввода, формат, запрет, единый шаблон UI.
- Правка, начинающаяся со слов «в таком-то экране» — почти всегда класс шире одного экрана.
- Ревью показало находку, которая по формулировке может встречаться не единожды.

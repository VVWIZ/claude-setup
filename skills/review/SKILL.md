Проведи ревью перед запуском: $ARGUMENTS

## Правила
- **НИКОГДА не редактируй файлы** — только читай и анализируй
- Если нашёл блокер — сразу скажи **НЕ ЗАПУСКАТЬ** с объяснением
- Вердикт в конце: ✅ можно запускать / ⚠️ с оговорками / 🛑 нельзя запускать
- **`--jury`** — включить режим слепого параллельного жюри (см. секцию «Режим слепого жюри» ниже). Без флага — обычный одиночный проход.

## Что проверять

### 1. Ошибки и баги
- Синтаксические ошибки
- Undefined переменные, несуществующие функции
- Неправильные типы данных, сравнения
- Незакрытые соединения, утечки ресурсов
- Бесконечные циклы, рекурсия без выхода

### 2. Безопасность (быстрая проверка)
- Пользовательский ввод попадает в SQL / HTML / shell без фильтрации?
- Новые credentials в коде?
- Открытые эндпоинты без авторизации?

### 3. Совместимость
- Работает ли на текущей версии рантайма (Node.js / PHP / Go / и т.д.)?
- Нет ли зависимостей от пакетов, которых нет на сервере?
- Конфликты с существующим кодом

### 4. Побочные эффекты
- Затрагивает ли другие модули?
- Меняет ли структуру БД?
- Меняет ли конфиги, права, переменные окружения?
- Может ли сломать существующий функционал?

### 5. Качество
- Логирование ошибок (не молчаливый провал)
- Обработка edge cases (пустые данные, null, большие объёмы)
- Нет ли debug-кода (console.log, var_dump, print, fmt.Println для отладки)

## Формат отчёта

### Вердикт: ✅ / ⚠️ / 🛑

### 🛑 Блокеры (нельзя запускать пока не исправлено)
| # | Проблема | Файл:строка | Почему блокер |

### ⚠️ Предупреждения (можно запускать, но желательно исправить)
| # | Проблема | Файл:строка | Риск |

### ℹ️ Замечания
| # | Замечание | Файл:строка |

### Затронутые модули
- Список модулей/файлов, которые могут быть затронуты изменениями

### Чек-лист перед запуском
- [ ] Бэкап БД сделан
- [ ] Бэкап файлов сделан
- [ ] Протестировано на dev/staging
- [ ] ...

## Режим слепого жюри (`--jury`)

Опциональный режим для high-stakes ревью (прод / security-чувствительный код / крупный diff). Включается флагом: `/review staged --jury` или `/review <цель> --jury`. Без флага — обычный одиночный проход (см. выше). Жюри спавнит субагентов **только при явном `--jury`**, не автоматически.

**Механика (зеркало minimise loop-evaluate + review-implementation):**

1. Раздать до **4 параллельных субагентов** (`max_concurrent: 4`) — по одному на ось. Каждый судит **только свою ось вслепую**: получает лишь код/diff + свой критерий (rubric). НЕ передавать ему ни историю сессии, ни выводы других судей — против якорения и группового согласия.
2. Оси (name → rubric-вопрос):
   - **correctness** → «Есть ли баги, ошибки логики, неверные типы/сравнения, необработанные edge-cases (null / пусто / большие объёмы), утечки ресурсов, незакрытые соединения, бесконечные циклы?»
   - **security** → «Попадает ли пользовательский ввод в SQL / HTML / shell без фильтрации? Новые credentials в коде? Открытые эндпоинты без авторизации?»
   - **compatibility** → «Работает ли на текущем рантайме и зависимостях? Ломает ли существующий функционал? Побочные эффекты на другие модули / БД / конфиги / права / переменные окружения?»
   - **quality** → «Нет ли лишней сложности (over-engineering), дублирования, debug-кода (console.log / var_dump / print), молчаливых провалов? Логируются ли ошибки? Покрыто ли изменение поведения тестами?»
3. Каждый судья **сверяет находки с реальным кодом** перед репортом (не выдумывает по описанию) и возвращает находки с severity **high** / **medium**.
4. Все судьи — на модели скилла (**Opus**), различаются **только критерием, не моделью** (как в репозитории minimise — persona-, не model-дифференциация).

**Свод (делает главный цикл):**
- Собрать находки всех судей, снять дубли, отранжировать по severity.
- Разложить в стандартный «Формат отчёта» выше (🛑 блокеры / ⚠️ предупреждения / ℹ️ замечания) + вердикт ✅/⚠️/🛑.
- Детерминированная последняя строка отчёта: **`REVIEW: PASS`** (ноль high-находок) или **`REVIEW: FAIL`** (есть хотя бы одна high) — для машиночитаемого гейта.

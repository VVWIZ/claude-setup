## Шаг 1: Аудит текущей обработки ошибок

### Go (основной стек)
Grep паттерны:
- `if err != nil` — общий объём обработки
- Проглоченные ошибки: `_ = ` перед вызовами, возвращающими error; `_, _ =`; пустые ветки `if err != nil { }`
- Голый проброс без контекста: `return err` (vs `fmt.Errorf("...: %w", err)`)
- `panic(` вне main/init — паника как control flow
- `errors.New(` / `fmt.Errorf(` разбросанные строки-ошибки vs sentinel-ошибки (`var ErrX = errors.New`)
- Сравнение ошибок строками: `err.Error() ==`, `strings.Contains(err.Error()`
- Recovery: есть ли `recover()` middleware на HTTP/воркерах/горутинах
- Горутины без обработки: `go func()` внутри которых ошибки некуда деть

### Node.js / фронт (если есть в проекте)
- `try/catch` блоки, пустые catch: `catch.*\{\s*\}`
- `process.on('uncaughtException')`, `unhandledRejection` — глобальные обработчики
- `.catch()` на промисах; забытые await

### PHP (легаси, если встретится)
- `set_error_handler` / `set_exception_handler`, пустые catch

## Шаг 3: Предложение стандарта

Предложи единую систему, адаптированную под стек:

### Для Go (основной):
1. **Оборачивание с контекстом** — `fmt.Errorf("операция X: %w", err)` на каждом уровне, где добавляется смысл; без дублирования текста нижнего уровня
2. **Sentinel и кастомные типы** — `var ErrNotFound = errors.New(...)` для ветвления; кастомный тип с полями (код, entity) там, где нужен контекст; проверка только `errors.Is` / `errors.As`, никогда по строке
3. **Границы паники** — `panic` только для programmer error; `recover()` middleware на HTTP-хендлерах, воркерах очередей и в обёртке для горутин
4. **Ошибка наружу ≠ ошибка внутрь** — клиенту уходит код+безопасное сообщение (единый error-response формат), в лог уходит полная цепочка; внутренности (SQL, стек) наружу не текут
5. **Ошибки логируются один раз** — на границе (хендлер/воркер), не на каждом уровне проброса; формат лога — по стандарту `/observability-and-instrumentation`

### Для Node.js:
1. Базовый класс AppError (код, сообщение, контекст); глобальные обработчики uncaughtException/unhandledRejection с graceful shutdown; централизованный error-middleware

### Для PHP:
1. set_error_handler + set_exception_handler, единые коды ошибок

## Шаг 4: План внедрения

Покажи конкретный план:
```
1. Создать: [путь] — [описание утилиты/middleware]
2. Изменить: [путь] — [что поменять]
...
```

**Приоритет внедрения:**
1. Recovery на входных точках (быстрая победа — ловит всё что падает)
2. Проглоченные ошибки (убрать молчаливые провалы)
3. Оборачивание с контекстом на ключевых путях
4. Sentinel/типы + errors.Is/As (стандартизация ветвления)

Дождись одобрения перед внедрением.
